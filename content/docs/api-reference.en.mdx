## Authentication

The public V1 API uses generic Bearer keys: `mp_live_*` or `mp_test_*`.
Keys are isolated per MailPulse organization. Legacy `mp_filon_*` keys remain
accepted for compatibility, but new clients should use MailPulse keys.

```txt
Authorization: Bearer mp_live_xxx
Idempotency-Key: source_event_unique_id
```

## Contacts

```txt
POST /api/v1/contacts
GET /api/v1/contacts/{contact_id}
PATCH /api/v1/contacts/{contact_id}/preferences
```

Contacts stay generic. Client business identifiers belong in `metadata`, such as
`external_user_id` or `external_tenant_id`.

## Messages

```txt
POST /api/v1/messages
GET /api/v1/messages/{message_id}
```

Statuses: `queued`, `retrying`, `sent`, `delivered`, `read`, `failed`,
`cancelled`, `template_required`.

An email refused by the provider moves to `failed` and `error_code` gives the
cause: `email_bounced`, `email_complained`, `email_suppressed` (address on the
provider's suppression list) or `email_failed` (sending failure, reason in
`error_message`). A late event never moves a delivered, read or failed message
backwards. A complaint received after delivery unsubscribes the contact but
leaves the message `delivered` or `read`.

`GET /api/v1/messages/{message_id}` also returns `delivery_delays`, the delivery
delays reported by the provider (at most 20, newest first). A delay does not
change the status: the message stays `sent` while the provider retries.

```json
"delivery_delays": [
  { "occurred_at": "2026-09-23T10:45:00.000Z" }
]
```

## External applications

```txt
POST /api/v1/external-applications/{application_key}/commands
POST /api/webhooks/whatsapp/meta/{application_key}
```

Command requests include `x-external-organization-id`, `x-external-timestamp`,
and `x-external-signature`. The HMAC signature covers `timestamp + "." + rawBody`
and carries a key identifier:

```txt
x-external-signature: v1:key_id=<signature>
```

Applications send an `operation_key` and their own idempotency key:

```json
{
  "operation_key": "notification",
  "channel": "whatsapp",
  "recipient": { "type": "phone", "value": "+2250700000000" },
  "content": { "type": "text", "text": "Your notification is ready." },
  "metadata": { "idempotency_key": "client_event_987_recipient_123" }
}
```

For WhatsApp `text` commands, MailPulse permits delivery only while the recipient
has an active 24-hour external conversation window. A signed inbound Meta text
message opens or extends that window. Outside it, the command is durably rejected
with HTTP `422` and `rejection_code: "whatsapp_service_window_closed"`; use an
approved template command instead. Template commands remain permitted outside the
window.

### Document

A command can send a file:

```json
{
  "type": "document",
  "url": "https://files.example.com/statement.pdf",
  "filename": "statement.pdf",
  "mimeType": "application/pdf",
  "caption": "Optional text"
}
```

`url` must be HTTPS. `filename` is at most 120 characters, with no `/` or `\`.
`mimeType` (or `mime_type`) is `application/pdf`, `image/jpeg` or `image/png`.
`caption` is optional, at most 1024 characters. The recipient sees the real file
name. On Meta, a document is free-form content and follows the 24-hour window
rule, like `text`.

### Recipient consent

A command can require the recipient's explicit agreement before writing to them.
The request text is written by the client application:

```json
{
  "operation_key": "notification",
  "channel": "whatsapp",
  "recipient": { "type": "phone", "value": "+2250700000000" },
  "content": { "type": "text", "text": "Your notification is ready." },
  "metadata": { "idempotency_key": "client_event_987_recipient_123" },
  "consent": {
    "request": { "text": "Hello, do you agree to receive our messages? Reply YES or NO." },
    "expiresInSeconds": 172800
  }
}
```

`request.text` is 1 to 1024 characters. `expiresInSeconds` (or
`expires_in_seconds`) defaults to 172800 (48 h) and is brought within 3600 to
604800. The expiry starts when the request is actually sent. Consent is held per
application, per sending account and per recipient.

| Consent state | What MailPulse does | Response |
|---|---|---|
| already granted | sends the content at once | as without consent (`202` accepted) |
| refused (NO or STOP) | sends nothing | `409 { "code": "consent_refused" }` |
| none, or expired | queues the request and keeps the content encrypted | `202 { "status": "consent_pending", "operationId": "…" }` |
| a request already pending | adds the content to the same wait, with no second request | `202 { "status": "consent_pending", "operationId": "…" }` |

A recipient who replied NO or STOP receives no further command from the
application through this account, with or without `consent`. A new YES from
them reactivates consent. A command whose consent expired is rejected with `422`
and `rejection_code: "consent_expired"`; send it again with a new idempotency
key to ask again.

Replies are read regardless of case, accents, punctuation and spaces. `OUI`,
`YES`, `OK`, `D'ACCORD` and `J'ACCEPTE` grant; `NON`, `NO`, `STOP`, `ARRÊT`,
`STOPPER` and `DÉSABONNER` refuse. A reply that settles a sent request is not
forwarded as an inbound message.

On Meta, the request is free-form text: it needs an open conversation window,
otherwise the command is rejected with `whatsapp_service_window_closed`. On
WhatsApp Web, consent-gated sends follow the pacing described on the WhatsApp
page.

### Callbacks to the application

MailPulse pushes provider events to the endpoints registered for the
application. Every call carries `x-external-event`, `x-external-timestamp` and
`x-external-signature`, signed with the endpoint secret in the same
`v1:key_id=...` format. An endpoint only receives the events it subscribes to.

```json
{
  "event_id": "wamid.ABC",
  "sender": { "phone": "+2250700000000" },
  "message": { "text": "NOTES" },
  "timestamp": "1750030073"
}
```

```json
{
  "event_id": "wamid.ABC:delivered",
  "operation_id": "cmd_123",
  "idempotency_key": "your_idempotency_key",
  "message": { "provider_message_id": "wamid.ABC", "status": "delivered" },
  "recipient": { "phone": "+2250700000000" },
  "error": null,
  "timestamp": "1750030073"
}
```

The first body is `whatsapp.inbound_message`, the second is
`whatsapp.message_status`. `message.status` carries the provider vocabulary:
`sent`, `delivered`, `read` or `failed`. On `failed`, `error` holds the code and
title reported by Meta.

`idempotency_key` and `operation_id` echo the original command, so a status can
be matched to its send without storing a MailPulse identifier. A status that
matches no command of the application is never forwarded. Statuses only move
forward, and a status can automatically reconcile a submission whose provider
response was lost.

### Consent and delivery events

These events share one payload, and an endpoint only receives those it
subscribes to:

```json
{
  "event": "consent.granted",
  "operationKey": "notification",
  "idempotencyKey": "client_event_987_recipient_123",
  "operationId": "cmd_123",
  "recipient": "+2250700000000",
  "occurredAt": "2026-09-25T16:00:00.000Z"
}
```

| Event | When |
|---|---|
| `consent.requested` | the consent request actually left |
| `consent.granted` | YES reply |
| `consent.refused` | NO or STOP reply; the held content is cancelled |
| `consent.expired` | no reply before the deadline; the held content is abandoned |
| `message.sent` | the content was accepted by the provider |
| `message.delivered` / `message.read` | delivery or read receipt, on Meta and on WhatsApp Web |
| `message.failed` | the content could not be delivered |

`message.*` also carries `messageId`, and `message.failed` a `failureCode`. A
recipient who already agreed only produces `message.*`. Each held command gets
its own events; a YES or STOP written with no command waiting produces a single
`consent.*`, with `operationKey`, `idempotencyKey` and `operationId` set to
`null`. Events are emitted once, even when the provider replays its webhook.

## Templates

```txt
POST /api/v1/templates
GET /api/v1/templates
PATCH /api/v1/templates/{template_key}
```

Templates may contain client business language, but MailPulse does not model the
client business domain. For WhatsApp, free-form messages outside the 24h service
window return `template_required`; WhatsApp templates must be approved.

## Conversations

```txt
GET /api/v1/conversations
GET /api/v1/conversations/{conversation_id}/messages
```

MailPulse groups messages by conversation and stores the WhatsApp service window
when available.

## Outgoing webhooks

```txt
POST /api/v1/webhooks
GET /api/v1/webhooks
DELETE /api/v1/webhooks/{webhook_id}
```

Events contain `event_id`, `type`, `tenant_id`, `created_at`, and `data`.
Requests are signed with HMAC SHA-256:

```txt
mailpulse-event-id: evt_xxx
mailpulse-timestamp: 1782996000
mailpulse-signature: v1=<signature>
```

The signature is computed over `timestamp + "." + rawBody` with the webhook
secret shown once at creation time.

## Client examples

Client applications generate idempotency keys, build business content, and pass
external identifiers through `metadata`.
MailPulse owns only technical communication concerns: channels, templates,
statuses, webhooks, retries, tenant isolation, and the WhatsApp window.
