## Authentification

L’API publique V1 utilise des clés Bearer génériques `mp_live_*` ou `mp_test_*`.
Les clés sont isolées par organisation MailPulse. Les anciennes clés `mp_filon_*`
restent acceptées comme compatibilité, mais les nouveaux clients doivent utiliser
les clés MailPulse.

```txt
Authorization: Bearer mp_live_xxx
Idempotency-Key: source_event_unique_id
```

## Contacts

```txt
POST /api/v1/contacts
GET /api/v1/contacts/{contact_id}
PATCH /api/v1/contacts/{contact_id}/preferences
```

Les contacts restent génériques. Les identifiants métier du client doivent aller
dans `metadata`, par exemple `external_user_id` ou `external_tenant_id`.

## Messages

```txt
POST /api/v1/messages
GET /api/v1/messages/{message_id}
```

Exemple :

```json
{
  "channel": "whatsapp",
  "recipient": { "type": "phone", "value": "+2250700000000" },
  "content": {
    "type": "template",
    "template_key": "absence_alert",
    "locale": "fr_CI",
    "variables": { "parent_name": "M. Kouassi" }
  },
  "metadata": {
    "external_user_id": "parent_123",
    "external_event_id": "absence_987",
    "source_app": "klassci"
  },
  "idempotency_key": "klassci_absence_987_parent_123"
}
```

Statuts possibles : `queued`, `retrying`, `sent`, `delivered`, `read`, `failed`,
`cancelled`, `template_required`.

## Templates

```txt
POST /api/v1/templates
GET /api/v1/templates
PATCH /api/v1/templates/{template_key}
```

Les templates peuvent contenir du vocabulaire métier client, mais MailPulse ne
modélise pas ce métier. Pour WhatsApp, les messages libres hors fenêtre de 24h
sont refusés avec `template_required`; les templates WhatsApp doivent être
approuvés.

## Conversations

```txt
GET /api/v1/conversations
GET /api/v1/conversations/{conversation_id}/messages
```

MailPulse regroupe les messages par conversation et conserve la fenêtre de
service WhatsApp lorsqu’elle existe.

## Webhooks sortants

```txt
POST /api/v1/webhooks
GET /api/v1/webhooks
DELETE /api/v1/webhooks/{webhook_id}
```

Chaque webhook sortant contient :

```json
{
  "event_id": "evt_xxx",
  "type": "message.queued",
  "tenant_id": "org_xxx",
  "created_at": "2026-07-02T10:00:00.000Z",
  "data": {}
}
```

Les requêtes sont signées avec HMAC SHA-256 :

```txt
mailpulse-event-id: evt_xxx
mailpulse-timestamp: 1782996000
mailpulse-signature: v1=<signature>
```

La signature se calcule sur `timestamp + "." + rawBody` avec le secret affiché
une seule fois lors de la création du webhook.

## Compatibilité Filon et Klassci

Filon et Klassci restent des applications clientes. Elles doivent générer leurs
propres clés d’idempotence, construire le contenu métier et transmettre les
identifiants externes dans `metadata`. MailPulse gère uniquement les contraintes
techniques : canaux, templates, statuts, webhooks, retries, isolation tenant et
fenêtre WhatsApp.
